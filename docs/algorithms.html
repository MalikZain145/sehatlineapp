Queueing & Priority Algorithms

Every algorithm that runs the SehatLine OPD queue — for each one: what it is, why we use it, its formula, a fully worked example step by step, and the exact backend file it lives in.

The nine algorithms

  1. Priority Scoring (rule-based triage)
  2. Priority-Ordered Queue (FCFS within a class)
  3. Position-Based Wait Estimate
  4. Least-Loaded Doctor (server pooling)
  5. Erlang C — Probability of Waiting
  6. M/M/s Multi-Server Model + Little's Law
  7. Cobham's Non-Preemptive Priority Waits
  8. Lag-SIPP Doctor Staffing
  9. AI/ML Triage Ensemble (+ rule fallback)

How they fit together: when a patient joins, Priority Scoring (1) — helped by the ML triage model (9) — gives them a score; the Priority-Ordered Queue (2) sorts everyone by that score; the patient sees a live ETA from the Position estimate (3); a free doctor is chosen by Least-Loaded pooling (4). Behind the scenes, Erlang C (5), the M/M/s model (6), Cobham priority waits (7) and Lag-SIPP staffing (8) predict waiting times and tell the hospital how many doctors to put on duty.

ALGORITHM 01

Priority Scoring (Rule-Based Triage)

📄 src/modules/patient/services/priority.service.js → computePriority()
Why we use it

A hospital queue must not be pure first-come-first-served — a person with chest pain cannot wait behind 20 routine check-ups. This algorithm reads a patient's age, conditions and status and gives a single, transparent priority number so the sickest and the most vulnerable are seen first. It is rule-based on purpose: the doctor can always see why someone was prioritised.

Aasan lafzon mein: har mareez ko ek "urgency number" de do — jitna zyada beemar/buzurg, utna bara number, utni jaldi baari.

Formula
score = base(level) + boosts
base  =  critical 1000  ·  high (pregnant/disabled) 700  ·  elderly 400  ·  normal 100
boosts  =  +100 if (critical and elderly)  ·  + min(age − 50, 40) for the elderly band

Level test order: critical (a heart/stroke/breathing/etc. keyword) → pregnancy/disability → elderly (age ≥ 50) → normal.

✎ Worked example

Given four patients arrive together: A = age 68, "chest pain" · B = age 72, no critical condition · C = age 30, pregnant · D = age 25, routine.

  1. Patient A — "chest pain" is a critical keyword → level critical, base = 1000. A is also elderly (68 ≥ 50) → +100 boost. score = 1000 + 100 = 1100
  2. Patient B — no critical condition, not pregnant/disabled, but 72 ≥ 50 → level elderly, base = 400. Elderly boost = min(72 − 50, 40) = min(22, 40) = 22. score = 400 + 22 = 422
  3. Patient C — pregnant → level high, base = 700, no extra boost. score = 700
  4. Patient D — nothing special → level normal. score = 100
  5. Higher score = seen sooner, so the serving order becomes A → C → B → D. Notice a critical 68-year-old (A) correctly beats a healthy 72-year-old (B), and a pregnant patient (C) beats a normal elderly (B).
Scores: A = 1100, C = 700, B = 422, D = 100 → order A, C, B, D
ALGORITHM 02

Priority-Ordered Queue (FCFS within a class)

📄 priority.service.js → orderByPriority()  ·  appointment.controller.js → getActiveAppointment()
Why we use it

Scoring alone is not a queue. This step actually orders everyone: highest score first, and when two patients have the same score, the one who arrived earlier goes first (fair First-Come-First-Served within a priority class). Your live "patients ahead of you" number is just your position in this sorted list.

Aasan lafzon mein: pehle score se sort karo; barabar score walon mein jo pehle aaya woh aage — phir jitne log tumse upar hain, wahi "ahead of you".

Formula (comparison rule)
sort by   priorityScore ↓   then   issuedAt ↑   (appointments: score ↓ → slot time ↑ → bookedAt ↑)
patients ahead of you  =  index of your token in the sorted list
✎ Worked example

Given four tokens with scores & arrival times: T1 400 @ 9:10 · T2 700 @ 9:05 · T3 400 @ 9:02 · T4 100 @ 9:00 (you are T4).

  1. Sort by score (high → low): 700, 400, 400, 100 → T2, then the two 400s, then T4.
  2. Tie-break the two 400-score tokens by earlier issuedAt: T3 @ 9:02 is before T1 @ 9:10 → T3 before T1.
  3. Final order: T2 (700) → T3 (400) → T1 (400) → T4 (100)
  4. You are T4, sitting at index 3 (the 4th person). patients ahead of you = 3
Serving order T2, T3, T1, T4 — you (T4) have 3 patients ahead
ALGORITHM 03

Position-Based Wait Estimate

📄 queueing.service.js → estimateWaitForPosition()  ·  token.controller.js → estimateWaitMin()
Why we use it

Once a patient knows they are, say, 7th in line, they want an ETA. With s doctors each taking about c minutes, the queue drains at s/c patients per minute, so a simple, honest estimate is possible without heavy maths — perfect for a live screen.

Aasan lafzon mein: jitne log aage hain × har mareez ka time ÷ kitne doctor kaam kar rahe — bas.

Formula
wait ≈ patientsAhead × cs    minutes
token variant (whole service cycles): wait = ⌈(position − 1) / s⌉ × c
c = mean consultation minutes, s = on-duty doctors.
✎ Worked example

Given you are at position 7, there are s = 3 doctors on duty, and each consultation takes c = 10 minutes.

  1. People ahead of you = 7 − 1 = 6 (or 7 counting your own slot — the linear formula uses "ahead").
  2. Linear estimate: (6 × 10) / 3 = 60 / 3 = 20 min  (using 7 ahead → 70/3 ≈ 23 min — either is a fair live estimate).
  3. Cycle variant: cycles = ⌈(7 − 1)/3⌉ = ⌈6/3⌉ = ⌈2⌉ = 2 full rounds of doctors.
  4. Wait = cycles × c = 2 × 10 = 20 min. Both methods agree ≈ 20 minutes.
Estimated wait ≈ 20 minutes
ALGORITHM 04

Least-Loaded Doctor (Server Pooling / Load Balancing)

📄 queueing.service.js → leastLoadedDoctor()
Why we use it

Queueing theory's single biggest lever to cut waiting is server pooling: one shared queue feeding every free doctor beats separate per-doctor lines (no one sits idle while another line is long). When routing a new patient, we send them to the doctor with the shortest current line.

Aasan lafzon mein: jis doctor ke paas sab se kam mareez hain, naya mareez usi ko do — line balance rahe.

Formula
chosen doctor = arg mind   load(d)   (the doctor with the fewest assigned patients)
✎ Worked example

Given three on-duty doctors with current lines: Dr A = 5 waiting · Dr B = 2 waiting · Dr C = 4 waiting.

  1. Compare loads one by one, keeping the smallest: start best = A (5).
  2. B has 2 < 5 → best = B (2).
  3. C has 4, but 4 > 2 → best stays B.
  4. The new patient is routed to Dr B, evening out the three lines.
Route to Dr B (load 2 — the shortest line)
ALGORITHM 05

Erlang C — Probability of Waiting

📄 src/modules/patient/services/queue.engine.js → erlangC()  ·  also in queueing.service.js
Why we use it

Before predicting how long people wait, we need the chance they wait at all — i.e. the probability that all s doctors are busy when a patient arrives. Erlang C is the classic call-centre / clinic formula for exactly this, and it is the engine inside the full M/M/s model (next section).

Aasan lafzon mein: ye batata hai ke naya mareez aaye to kitni probability hai ke saare doctor busy hain aur usay ruk-na paray.

Formula
offered load   a = λμ    utilisation   ρ = as
C(s, a) = ass! (1 − ρ)   Σk=0s−1 akk!  +  ass! (1 − ρ)  
λ = arrivals per hour, μ = patients served per hour per doctor, s = doctors. If ρ ≥ 1 the queue is unstable → C = 1 (everyone waits).
✎ Worked example

Given λ = 18 patients/hour, 10-minute consultations → μ = 60/10 = 6 per hour per doctor, and s = 4 doctors.

  1. Offered load: a = λ/μ = 18/6 = 3 Erlangs. Utilisation ρ = a/s = 3/4 = 0.75 (< 1 → stable).
  2. Bottom sum Σ = a⁰/0! + a¹/1! + a²/2! + a³/3! = 1 + 3 + 4.5 + 4.5 = 13
  3. The "all busy" term aˢ/s! = 3⁴/4! = 81/24 = 3.375, then ÷ (1 − ρ): 3.375 / 0.25 = 13.5
  4. Combine: C = 13.5 / (13 + 13.5) = 13.5 / 26.5 = 0.509
C ≈ 0.509 → about a 51% chance an arriving patient has to wait
ALGORITHM 06

M/M/s Multi-Server Model + Little's Law

📄 queue.engine.js → mmsMetrics()  ·  queueing.service.js → metrics()  ·  shown on the admin dashboard (system.controller.js)
Why we use it

This is the heart of the capacity model. "M/M/s" = random (Markov) arrivals, random service times, s servers (doctors) sharing one queue. From just λ, μ and s it predicts the average wait Wq, the queue length Lq, utilisation ρ and time-in-system W — the numbers the hospital plans around. Little's Law (L = λW) is what turns a "time" into a "count".

Aasan lafzon mein: λ (kitne aa rahe), μ (kitni tezi se dekha ja raha), s (kitne doctor) do — ye average wait aur line ki lambai bata deta hai.

Formula
Wq = C(s, a)sμ − λ   (avg wait in queue)
Lq = λ · Wq    W = Wq + 1μ    L = λ · W   ← Little's Law
✎ Worked example

Given the same clinic: λ = 18/hr, μ = 6/hr, s = 4, and from Algorithm 05 we already have C = 0.509.

  1. Service capacity sμ = 4 × 6 = 24 patients/hr, which is > λ = 18, so the system is stable.
  2. Average wait in queue Wq = C/(sμ − λ) = 0.509/(24 − 18) = 0.509/6 = 0.0849 hr = 5.1 minutes.
  3. Average number waiting (Little's Law) Lq = λ · Wq = 18 × 0.0849 = 1.53 patients.
  4. Time in system W = Wq + 1/μ = 0.0849 + 0.1667 = 0.2516 hr = 15.1 minutes (wait + the 10-min consult).
  5. People in the clinic L = λ · W = 18 × 0.2516 = 4.53 patients on average.
Wq ≈ 5.1 min · Lq ≈ 1.5 waiting · W ≈ 15.1 min · L ≈ 4.5 in clinic
ALGORITHM 07

Cobham's Non-Preemptive Priority Waits

📄 queue.engine.js → priorityWaits()
Why we use it

The plain M/M/s wait is one average for everybody. But we have priority classes (critical, elderly, normal) sharing the same doctors — so a critical patient should have a shorter predicted wait than a normal one. Cobham's approximation splits the single aggregate wait across the classes, "non-preemptive" meaning a consultation in progress is never interrupted.

Aasan lafzon mein: aik average wait ko priority classes mein baant deta — upar wali class ka wait kam, neeche wali ka zyada.

Formula
for class k (highest first):   ρk = λksμ,   σk = ρ1+…+ρk
Wqk = Wqagg · (1 − ρagg)(1 − σk−1)(1 − σk)
σk−1 = cumulative load ABOVE this class; σk includes it. Wqagg, ρagg come from the M/M/s model.
✎ Worked example

Given μ = 6, s = 4, and the λ = 18 split into classes: Critical λ = 3, Elderly λ = 6, Normal λ = 9. From Algorithm 06: Wqagg = 5.09 min, ρagg = 0.75.

  1. Per-class loads: ρ_crit = 3/24 = 0.125 · ρ_eld = 6/24 = 0.25 · ρ_norm = 9/24 = 0.375 (they sum to 0.75 = ρ_agg ✓).
  2. Numerator (same for all) = Wq_agg·(1 − ρ_agg) = 5.09 × 0.25 = 1.273.
  3. Critical: σ₀ = 0, σ₁ = 0.125 → denom = (1)(0.875) = 0.875 → Wq = 1.273/0.875 = 1.45 min.
  4. Elderly: σ₁ = 0.125, σ₂ = 0.375 → denom = (0.875)(0.625) = 0.547 → Wq = 1.273/0.547 = 2.33 min.
  5. Normal: σ₂ = 0.375, σ₃ = 0.75 → denom = (0.625)(0.25) = 0.156 → Wq = 1.273/0.156 = 8.15 min.
Critical ≈ 1.5 min · Elderly ≈ 2.3 min · Normal ≈ 8.2 min — priority visibly pays off
ALGORITHM 08

Lag-SIPP Doctor Staffing

📄 queue.engine.js → lagSippStaffing() + serversForTarget()
Why we use it

Demand changes through the day. "SIPP" (Stationary Independent Period-by-Period) picks the minimum doctors each hour to hit a target wait — but on its own it under-staffs, because the patients who arrive late in a busy hour are still waiting when the next, quieter hour begins. Lag-SIPP fixes this by shifting each period's need forward by one lag, so the tail of a rush stays covered.

Aasan lafzon mein: har ghante ke liye zaroori doctors nikalo, phir busy ghante ka bojh agle ghante par bhi rakh do taake rush ki dum bhi clear ho jaye.

Formula
need(period) = smallest s with M/M/s stable and Wq ≤ target
recommendedi = max( needi,   needi − lag )   (lag = 1 period)
✎ Worked example

Given μ = 6/hr, target Wq ≤ 15 min, lag = 1. Forecast arrivals: 8 AM λ = 6 · 9 AM λ = 18 · 10 AM λ = 30 · 11 AM λ = 12.

  1. Find each hour's independent need (smallest s that is stable and gives Wq ≤ 15 min):
    Hourλsmallest stable sWq at that sneed
    8 AM6s = 2 (ρ = 0.5)3.3 min ✓2
    9 AM18s = 4 (ρ = 0.75)5.1 min ✓4
    10 AM30s = 6 (ρ = 0.83)5.9 min ✓6
    11 AM12s = 3 (ρ = 0.67)4.4 min ✓3
    (s must exceed the load a = λ/μ for stability, e.g. 30/6 = 5, so s ≥ 6.)
  2. Raw SIPP need = [2, 4, 6, 3].
  3. Apply the lag shift, recommendedi = max(needi, needi−1): 8 AM → 2 · 9 AM → max(4,2)=4 · 10 AM → max(6,4)=6 · 11 AM → max(3,6)=6.
  4. The 11 AM slot jumps from 3 to 6 doctors: Lag-SIPP keeps extra doctors on to clear the 10 AM surge that spills over — the whole point.
Recommended doctors: 8AM = 2 · 9AM = 4 · 10AM = 6 · 11AM = 6
ALGORITHM 09

AI/ML Triage Ensemble (with rule-based fallback)

📄 src/services/priority.ml.service.js (scorePatient, buildPatient) → Python ml-service/ · fallback: priority.service.js
Why we use it

Rules (Algorithm 01) are transparent but blunt. When a patient has recent vitals — blood pressure, heart rate, SpO₂, blood sugar, temperature — a trained model can spot danger the keywords miss (e.g. a "normal" patient whose SpO₂ is 88). SehatLine sends the patient's feature vector to a trained Gradient Boosting + neural-network (MLP) ensemble; if that service is unreachable, it gracefully falls back to the rule score, so booking never breaks.

Aasan lafzon mein: mareez ke vitals ek trained model ko do, woh smarter urgency score de; agar model band ho to rule-wala score chal jata — kabhi rukta nahi.

Method & fallback
score = fensemble( age, conditions, systolic, diastolic, heartRate, spo2, bloodSugar, temperature, … )
fensemble = average of a Gradient-Boosting model and a neural MLP (learned from data — not a closed formula)
if ML service times out (> 1.5 s)  →  score = computePriority(…)  (the rules from Algorithm 01)
✎ Worked example (the flow — a learned model isn't solved by hand)

Given a patient, age 55, marked "routine", but latest vitals: SpO₂ = 88%, heart rate = 122, BP = 150/95.

  1. buildPatient() assembles the feature vector from the user + their most recent Vital record: {age:55, spo2:88, heartRate:122, systolic:150, …}.
  2. It is POSTed to the Python ML service; the ensemble reads the low SpO₂ + high HR and returns a high urgency, e.g. { score: ~900, level: "high" } — even though the rules alone would have said "elderly, 400".
  3. That ML score is stored as the token's priorityScore and used by Algorithm 02 to place the patient — so the deteriorating patient rises correctly.
  4. Fallback path: if the ML service is down, the catch keeps the rule score from computePriority() (here age 55 → elderly 400 + 5 = 405), so the queue still works, just with the simpler rule.
ML raises a silently-critical patient above the rules; if ML is offline, the rule score keeps the app running
